17: 1  What you submit 
18: Three deliverables. They are marked together against one rubric (§5), but each carries evidence the 
19: others cannot: the repository shows that it works, the video shows that it works on your machine, 
20: end to end, and the report shows that you understand why it works and where it does not. 
21: Deliverable Format What it must be 
22: 1. Repository GitHub URL A runnable repository with a README that takes a marker from a 
23: clean machine to a working run. Public, or private with the module 
24: team added as collaborators. 
25: 2. Video demo YouTube URL (unlisted) A 10-minute recorded demonstration of the running system, its 
26: evaluation, and its guardrails.

30: 2  Deliverable 1 — the GitHub repository 
31: 2.1  What the repository must contain 
32:  The full source of your agent, including tool definitions, prompts, and the controller loop. 
33:  README.md — the run instructions, specified in §2.2. This is the single most important file in the 
34: repository. 
35:  requirements.txt with pinned versions, or an equivalent lock file. 
36:  .env.example listing every environment variable your system reads, with dummy values. The real 
37: .env must be in .gitignore and must never be committed. 
38:  Your evaluation harness and its task set, so the numbers in your report can be reproduced. 
39:  Your tests. These must run with no API key and no network access. 
40:  A LICENCE file if you intend the work to be reusable, and an acknowledgement of any third-party 
41: code or data.

45: 2.2  What your README must contain 
46: A marker will clone your repository onto a clean machine and follow your README literally. Write 
47: it for that reader — not for someone who already has your project set up. Include, in this order: 
48: 1. What it does — one paragraph. The problem, the domain, and what the agent actually does. 
49: 2. Prerequisites — Python version, and the model runtime (Ollama, or the hosted provider and 
50: which snapshot). 
51: 3. Install — exact, copy-pasteable commands, from git clone to installed dependencies. 
52: 4. Configure — how to copy .env.example to .env, and which two variables switch the model 
53: provider. 
54: 5. Run — the single command that starts the system, and what the user should see when it works. 
55: 6. Test — the single command that runs the test suite, and the expected result. State plainly that it 
56: needs no API key and no network. 
57: 7. A worked example — one concrete input and the output it produces, so the marker can tell a 
58: correct run from a broken one. 
59: 8. Reproduce the evaluation — the command that runs your evaluation set, and the numbers it 
60: should print. These must match the numbers in your report. 
61: 9. The approval gate — where the consequential action lives, how to trigger it, and what the 
62: human reviewer sees. 
63: 10. Repository map — one line per directory, saying what lives there. 
64: 11. Limitations — what the system does not do, and what would break it. 
65: THE README IS MARKED BY BEING FOLLOWED 
66: Every year, Students lose implementation marks not because the system is poor but because it could 
67: not be started. Before you submit, have someone clone the repository into a fresh directory, follow only 
68: the README, and report where they got stuck. Fix that, then submit.  
69: If some step genuinely cannot be automated — a large model download, say — say so explicitly and give 
70: the expected time and disk cost.

73: Public is simplest and is recommended. If you keep the repository private, add the module team as 
74: collaborators before the deadline and say so in the report — an invitation that is still pending

89: 3.2  What to cover 
90: Ten minutes is a hard cap: marking stops at 10:00, and anything after that point is not seen. 
91: Rehearse against the clock. The breakdown below is a guide, not a rule — but every row in it carries 
92: marks somewhere in the rubric. 
93: Time What to show 
94: 0:00–1:00 The problem, the domain, and why an agent — what an agentic approach buys you over a non-
95: agentic baseline. This is the criterion teams most often lose. 
96: 1:00–2:00 Architecture: the agents, the tools and their permission tiers, and which patterns you used 
97: (planning, memory, multi-agent, oversight). 
98: 2:00–5:30 The system running, end to end, on a real task. Show at least one case that goes wrong and how the 
99: system handles it — a clean happy path alone is weak evidence. 
100: 5:30–7:30 Evaluation: your metrics, your task set, and your actual results, including cost and latency. Name a 
101: failure mode you did not fix. 
102: 7:30–9:00 Responsible design: the risk you designed against, your guardrails, and the approval gate firing 
103: on a consequential action. 
104: 9:00–

108: 3.3  Recording quality 
109:  Record at 1080p and enlarge your terminal and editor fonts before you start. Text that is 
110: unreadable at the marker's screen size cannot be credited. 
111:  Speak over the demo — narrate what you are doing and why. A silent screen recording scores 
112: poorly on communication. 
113:  Leave YouTube's automatic captions on, and correct them if they mangle technical terms. 
114:  Use no copyrighted music. A video muted or taken down by a copyright claim is a missing 
115: deliverable. 
116:  Blur or avoid showing real API keys, personal data, or anything else you would not publish. 
117: TEN MINUTES MEANS TEN MINUTES 
118: A 14-minute video is marked on its first ten minutes. If your limitations section sits at 12:30, it is not 
119: marked. Cut the setup and the code tour — the repository already shows the code. Spend the time on 
120: the system running, the evaluation, and the guardrails.
